- ロス 20% まで合格したのは、GNS、msquic、SLikeNet、lsquic、coop_rudp。ENet・KCP・LiteNetLib と TCP の 2 つは、再送の待ち時間が伸びて MD が秒単位で遅れる(C2)。yojimbo と quiche は、ロス 20% で LT の到達率か staleness が基準を外れる(C3)。
- ゆらぎ(jitter30-loss2)で LT を落とすのは、LT を unreliable sequenced で送る ENet・LiteNetLib・SLikeNet・coop_rudp。順序が入れ替わった古いものを捨てる。
- congest1m に合格したのは coop_rudp だけ。他は古い LT を捨てずに送り続け、回線の待ち行列(約 1 秒)か自分の中の送信待ちで遅れる。
- 5 秒の断(outage5)の後に戻ったのは、GNS、msquic-cancel-on-blocked、websocket、magiconion、yojimbo、SLikeNet、coop_rudp。15 秒の断(outage15)では、切断までの時間を 30 秒にした GNS・SLikeNet・yojimbo と、coop_rudp だけが合格した。
- 切断までの時間を 30 秒にしても、ENet・LiteNetLib・msquic は回線断(C4)で不合格のまま。再送の待ち時間が断の間に伸び、断が明けた後の最初の再送が遅れる。
- raw_udp は再送を持たないので、MD のある条件はロスがあれば C2 で落ちる(物差しとして期待どおり)。

### KCP

既定の設定(`ikcp_create` のまま)では、MD の遅延の大半は KCP の送信キューでの待ち時間。計測窓の間の `ikcp_waitsnd` の最大(セグメント数、1 セグメント = MD 1 件 = 100 ms 分)は loss10 で 25〜29、loss20 で 184〜187、outage15 で 186〜273 で、MD 遅延の最大(loss10 2.9 秒、loss20 21〜22 秒、outage15 19〜27 秒)とほぼ一致する。

- 高速再送は既定で無効(`fastresend=0`)。失ったセグメントはすべて時間切れまで待つ(`ikcp.c:286`, `:1045`)。
- 時間切れのたびに送信窓 cwnd を 1 に戻す(`ikcp.c:1126-1132`)。輻輳制御は既定で有効(`nocwnd=0`、`ikcp.c:288`, `:1017-1021`)。
- 送信と確認応答は 100 ms ごとの `ikcp_flush` でしか出ない(`interval=100`、`ikcp.c:39`, `:280`)。
- 時間切れのたびに再送の待ち時間を 2 倍以上にし、上限がない(`nodelay=0` のとき `rto += max(rto, rx_rto)`、`ikcp.c:1062-1063`)。
- `ikcp_send` は送信キューに足すだけで、長さを制限しない(`ikcp.c:507-529`)。

これらが重なり、ロスがあると 1 秒あたりに送り出せる MD が送る量(10 件/秒)を下回ってキューが伸びる(loss5・loss10・loss20・burst5x10 の C2)。loss20 では drain の 5 秒でも送り切れず、最終到達率が 0.76 / 0.80 になった。回線断(outage5 / outage15 の C4)は、倍々に伸びた再送が断の後まで来ないことと、断の間に溜まった分が cwnd 1 から少しずつしか出ないことによる。congest1m の MD(C3)も同じで、混雑した下りで時間切れが続き、キューが 135 セグメントまで伸びた。

### 混雑(congest1m)

coop_rudp 以外は全部が不合格だった。下りの負荷(約 1.3 Mbit/s)が容量(1 Mbit/s)を超え続けると、coop_rudp 以外は古い LT を自分から捨てずに送り続けた。

- 自分のキューを持たずに回線の待ち行列(約 1 秒)へ出す実装(ENet、GNS、LiteNetLib、yojimbo、SLikeNet、lsquic の LT、msquic-cancel-on-blocked、quiche-drop-old-dgram)は、下りの LT staleness p99 が 0.6〜1.4 秒で止まる。
- 自分の中に上限のないキューを持つ実装(msquic と quiche の datagram、KCP の MD、TCP 系)は、遅れが経過時間に比例して 13〜29 秒まで伸びる。
- KCP と raw_udp は LT を毎 tick、接続の番号順に続けて `sendto` する(`benchkit/src/sut.c:697`)。満杯の待ち行列には前の tick から空いた分しか入らず、後から入る接続が毎回落ちる(K`/net/sched/sch_netem.c#L525-L531`)。接続ごとの受信数を数えるビルドで測ると、0〜4 番は 949〜1000 件、5 番は 664〜992 件、6 番と 7 番は 46〜91 件だった。下りの LT staleness p99(27〜28 秒)は、ほとんど届かない後ろの接続の値(結果は `results-v2/dbg-20261107/{kcp,raw_udp}`)。

送る量が容量を超え続ける状況で遅延を低く保つには、ライブラリが待ち行列の伸びを見て送る量を落とし、送れない LT を捨てる必要がある。それをしないライブラリでは、アプリが送る量を落とす必要があり、送信待ちの量が見えること(C5)が前提になる。
