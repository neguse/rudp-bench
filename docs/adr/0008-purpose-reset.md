# ADR-0008: 目的の仕切り直し — 自分のゲームで「使える」RUDP を決める

- Status: **Draft**(未合意 — owner レビュー待ち)
- Date: 2026-11-05
- Supersede: ADR-0000(目的と成功条件)
- 凍結: ADR-0002, ADR-0004, ADR-0005, ADR-0006(この ADR の accept 以降、これらに基づく新しい測定はしない。記録として残す)
- 存続: ADR-0001(scenario の通信形状と LT/MD の区別。次の方法論 ADR の入力にする)
- Decision owner: project owner

## Context

### 出発点

ENet を実際に使ったところ、遅延とロスが少しある回線で reliable が使えなくなった。
本プロジェクトの元の問いは「そういう回線でも使える RUDP はどれか(自作を含む)」である。

### v1・v2 がこの問いに答えられなかった理由

1. **回線の悪さを振っていない。** v1 の canonical(`scenarios/canonical.json`)も v2 の reference campaign(`scripts/fleet/queues/ref1-enet/*/sweep.json`)も、回線を遅延 25 ms・ロス 1% に固定し、接続数だけを振る大規模ベンチだった。
2. **目的が広がった。** v1 の「ライブラリの横並び比較」から、ADR-0000 で「他人が自分の workload を再現して技術選択できる基盤と比較データ」になり、要求される厳密さが際限なく増えた。
3. **小さいほうのブレを潰していた。** 結果を桁で変えたのは測った実装そのものの違い(はめ込み方、既定設定、ベンチ側のバグ)だった。例: yojimbo の到達率 0.42→0.989([v2 設計](../log/2026-07-02-rudp-bench-v2-design.md))、GNS の到達率 0.086→0.943(ledger #13)、websocket client の誤計数(ledger #19)。一方で環境と反復による揺れは 1.3〜6%(ledger #26)だった。v2 の後半(doctor、drift gate、fleet、spot 対応)は主に後者に費やされ、reference 測定は 1 本も取れていない([current.md](../measurements/current.md))。

### 信頼できた成果

ledger のうち、ソースの該当行で仕組みまで説明した項目は、ベンチの作り方に依存しない知見として残っている。
ENet の throttle がロスで 0 まで落ちる(#11)、msquic が 16 秒で切断する(#17)、GNS の送信速度上限(#13)などである。

## Decision

### 1. 目的

本プロジェクトの目的は、**project owner のゲームで使う RUDP(既存ライブラリか自作か)を決めること**とする。
他人向けの再現基盤や比較データの提供は目的に含めない。

### 2. 「使える」の定義

ゲームの通信が成り立たなくなる振る舞いをしないことを「使える」とする。
回線が良いときの性能差は判断材料にしない。

1. **勝手に切らない。** 経路が生きている間はライブラリの判断で切断しない。切断までの時間をアプリが決められる。
2. **reliable の遅れに上限がある。** ロス下でも reliable の到達遅延が有限の範囲に収まり、再送待ちの倍々増加で秒単位に止まらない。
3. **混雑と、混雑によらないロスを取り違えない。** 混雑時は送る量を減らして遅延を低く保つ(bufferbloat させない)。混雑によらないロスには過剰に絞らない。
4. **回線が戻れば品質も戻る。** 悪い時間帯が過ぎた後、元の品質へ戻る。
5. **送信待ちの量がアプリから見える。** あふれそうなときにライブラリが黙って溜め込んだり捨てたりせず、アプリ側で送る量を落とす判断ができる。

各項目の数値基準は次の方法論 ADR で定める。

### 3. 問いの立て方

結果が大きく割れる問い(切れるか、遅延に上限があるか、戻るか)だけを扱う。
不合格が出たら、ソースで原因を説明できるまでを 1 つの結果とする。
順位付けと、数 % の差を判定する精度は求めない。

### 4. 2 種類のベンチ

- **劣悪ベンチ**(主): 少ない接続数で回線の悪さを振り、2 の各項目の合否を見る。
- **大規模ベンチ**(従): 劣悪ベンチに残った候補だけを、ゲームの想定人数 1 点で production 想定の instance type 上で動かし、CPU に余裕があるかだけを見る。

## Non-goals

- 他人が再現して技術選択するための基盤・比較表を作ること
- 全ライブラリの順位表を作ること
- 数 % の差を統計的に確定させること

## Consequences

- 次に方法論 ADR を書く。劣悪ベンチのシナリオ、2 の数値基準、実行環境を定める。シナリオは既存の枠組み(RMCAT の RFC 8867/8868/8869、IPPM の responsiveness draft、QUIC interop runner)を参照し、ゲームの通信(送る量がほぼ一定で、古いデータに価値がない)に合わせて読み替える。
- `servers/<lib>` の実装と設計ノート、`benchkit`、orchestrator の単発実行経路は残して使う。
- ledger のうち仕組みまで説明した項目は、ライブラリごとの知見として整理し直す。
- 凍結した ADR に基づく仕組み(fleet、campaign、drift gate、sentinel 等)と v1 のコードは、別の変更で撤去または凍結を明記する。ルート CLAUDE.md の campaign 向けの運用ルールも、この ADR の accept 後に改める。
