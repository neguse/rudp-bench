# ADR-0010: 劣悪ベンチ用に SUT を作り直す — 共通の負荷と計測、ライブラリごとの薄い層

- Status: **Draft**(未合意 — owner レビュー待ち)
- Date: 2026-11-06
- 依存: ADR-0008(目的と「使える」の定義)、ADR-0009(劣悪ベンチの条件と判定)
- Accept 時に置き換えるもの: ADR-0009 §4 の「treatment は `servers/<lib>` の現在の実装と設定のまま測る」
- Decision owner: project owner

## Context

### 今の `servers/` は旧目的のために作られている

`servers/` の各実装は「各ライブラリの最強実装を横並びで比べ、接続数を振って限界を見る」ために作った。
劣悪ベンチ(ADR-0009)はこの実装のまま回し、84 run がすべて VALID だった。不合格はどれもライブラリのソースで説明でき、測定器としては動いた([2026-11-05 の記録](../measurements/2026-11-05-badnet-local.md))。
一方で、劣悪ベンチの問いに対しては次の 2 点がずれている。

1. **ライブラリ固有の部分が小さく、共通の部分がライブラリの数だけ複製されている。** ENet・KCP・GNS では、client と server を合わせて約 1,900〜2,800 行ある。そのうちライブラリを直接呼ぶのは接続・送受信・切断の扱いの一部で、残りは引数の解釈、接続数を段階的に増やす処理、集計の出力である。
2. **設定が性能寄りになっている。** 例: ENet は混雑時に送る量を絞る仕組みを切り、タイムアウトを延ばしている(`servers/enet/client.c` の `tune_peer`)。劣悪ベンチで知りたいのは「ゲームで普通に使ったときに耐えるか」で、性能を上げるための設定は測る対象を変えてしまう。

### v1 にだけ実装があるライブラリ

次の 9 つは v1(`adapters/`)にだけ実装があり、劣悪ベンチでは測れない。

| 種類 | ライブラリ | v1 での位置づけ |
|---|---|---|
| 既存 | yojimbo、SLikeNet、RakNet、quiche、lsquic、UDT4 | 横並び比較の参加者 |
| 自作 | coop_rudp | 適応的な再送の待ち時間、重複排除、チャネルを持つ汎用の実装(`coop_rudp/`) |
| 自作 | apex_rudp | v1 の負荷に特化した実装。混雑への対応を意図的に持たず、一般の回線向けではないと明記(`adapters/apex_rudp/apex_rudp_adapter.cc` 冒頭) |
| 自作 | mini_rudp | 最小の参考実装。再送の待ち時間は 50 ms 固定 |

## Decision

### 1. 構成

- 負荷の生成、計測、orchestrator との制御のやり取りは、言語ごとに共通の 1 つだけ持つ。C と C++ のライブラリは `benchkit`、C# のライブラリは 1 つの共有ライブラリを使う。
- ライブラリごとに書くのは、接続、送信(LT と MD の振り分け)、受信、切断の検知、送信待ちの量の取得(ADR-0008 の C5。API があるものだけ)に限る。
- 接続数は固定値を 1 つ受け取るだけにする。接続数を段階的に増やす処理など、凍結した ADR のための機能は持たない。

### 2. 設定

- 各ライブラリは、まず **既定の設定** の treatment を持つ。値はライブラリの既定のままにする。
- 既定から変えた treatment を作るときは、ゲームで実際にそう使う理由を書く。性能を上げるためだけの変更はしない。
- LT と MD をどのチャネル・送信方法に載せるかは、ライブラリの文書かソースが勧める使い方に従い、出典を書く。

### 3. 候補

owner が決める。以下は草案の提案である。

| ライブラリ | 提案 | 理由 |
|---|---|---|
| 今の 7 つ(ENet、KCP、GNS、msquic、LiteNetLib、websocket、MagicOnion) | 入れる | 既に結果がある |
| yojimbo、SLikeNet、quiche、lsquic | 入れる | ゲームで使われうる既存の実装 |
| RakNet | 入れない | SLikeNet は RakNet から派生した実装で、系統として重なる |
| UDT4 | 入れない | 大きなデータを速く送るための実装で、ゲームの通信の形と違う |
| coop_rudp | 入れる | 自作の候補として最も機能が揃っている |
| apex_rudp、mini_rudp | 入れない | 一般の回線向けではない、または参考実装 |
| raw_udp | 物差しとして残す | 回線再現と計測器が正しく動くかを `base` 条件で確かめる |

### 4. 作り直しが正しいかの確かめ方

- 共通の部分、raw_udp、ENet を最初に作る。ENet は旧実装と同じ設定の treatment も作り、ADR-0009 の 12 条件の合否が 2026-11-05 の結果と一致することを確かめる(境目のセルは除く)。一致しなければ、他のライブラリには進まない。
- その後は 1 ライブラリずつ作り、既定の設定で 12 条件を回して記録する。旧実装と比べるのは ENet だけとする。

### 5. 撤去

- v1 一式(`harness/`、`adapters/`、`cmd/`、`internal/`、`scenarios/`、`tests/`、ルートの `CMakeLists.txt`、v1 用の `scripts/` と CI)は、この ADR の accept 後に消す。作り直しで v1 のコードを参考にするときは git の履歴から読む。
- 凍結した ADR(0002、0004、0005、0006)のための仕組み(orchestrator の中の campaign 向けの部分、`scripts/fleet`、bundle の配布)も同時に消す。
- 旧 `servers/<lib>` は、そのライブラリの新しい実装が記録まで済んだ時点で消す。

## Non-goals

- 大規模ベンチの実装(ADR-0008 の従のベンチ。劣悪ベンチで候補が絞れてから決める)
- 性能の比較と順位付け

## Consequences

- `docs/measurements/` の 2026-11-05 の結果は旧実装の記録として残す。判断には新しい実装の結果を使う。
- ルートの CLAUDE.md の「現行方針」「バトル」「rig 運用」「v1/v2」の節と README を、この ADR の accept 後に書き直す。
